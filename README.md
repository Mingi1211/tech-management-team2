# 학업나침반 — 광운대 기술과경영 2조

수강 조합의 **학기 부담을 주차 단위로 진단**하고, **관심분야에 맞는 학기별 수강 로드맵**을
제시하는 웹 서비스. 링크·QR로 접속하며 로그인과 개인정보 수집이 없다.

- 대상 학부 — 로봇학부 · 소프트웨어학부 · 정보융합학부
- 팀 구성 — 8명 (PM 1 · 개발 3 · DB 2 · 디자인/기획 2)

---

## 왜 만드는가

수강신청 도구는 **요일·시간이 겹치지 않는 조합**까지만 알려준다. 그러나 한 학기의 결과를
좌우하는 것은 시간표가 아니라 **과목 조합이 학기 중 언제 부담을 만드는가**이다.
시험기간에 팀 프로젝트 마감이 겹치는지, 매주 과제가 있는 과목을 몇 개나 담았는지는
지금 아무도 알려주지 않는다.

실제 수강한 선배들이 남긴 정량 데이터를 근거로 그 부담을 **개강 전에** 계산해 보여주고,
부담을 낮춘 대안 조합까지 제시한다.

## 설계 원칙

| | |
|---|---|
| **횟수가 아니라 시점** | 모든 부담을 주차(1~16) 단위 이벤트로 정규화해 저장한다. "과제 10회"로는 충돌을 계산할 수 없다 |
| **권한·개인정보 0** | 학교 시스템에 접근하지 않는다. 선배의 자발적 입력과 공개 교과과정표만 쓴다 |
| **`과목 × 교수 × 학기`** | 담당 교수가 바뀌면 운영이 달라지므로 개설 회차를 기본 단위로 삼는다 |
| **모르면 모른다고 표시** | 응답 수에 따라 신뢰도 A/B/C를 화면에 그대로 노출한다 |
| **교수 평가는 하지 않는다** | 과목의 운영 방식만 다룬다. 개인에 대한 점수·순위는 기능에서 제외 |

## 이 레포의 구성

```
app/                        Next.js 앱 (App Router)
  page.tsx                  선배 수강 경험 입력 폼
  api/reports/route.ts      제출 받기 → 검증 → Supabase 저장
  layout.tsx  globals.css
lib/report.ts               타입 · 주차 정규화 · 검증 (폼과 API 가 함께 쓴다)
db/
  schema.sql                Supabase 스키마 — 테이블 7개 · 트리거 · RLS · 집계 뷰
  README.md                 적용 방법과 권한 주의
docs/
  team-project-topic.md     주제안 전문 — 문제정의 · 범위 · R&R · 예상 질문 방어 시트
  plan/학업나침반-설계계획.pdf  설계 계획서 9쪽
  deck/학기예보.pptx          팀 공유용 덱 10장 · 프로토타입 화면 8장
prototype/collector/        초기 프로토타입 (claude.ai 아티팩트). 문항 검증용으로만 남겨 둔다
```

## 실행

```bash
npm install
cp .env.example .env.local     # Supabase URL 과 anon key 를 채운다
npm run dev                    # http://localhost:3000
```

`.env.local` 은 커밋되지 않는다. `service_role key` 는 어디에도 넣지 않는다.

## 배포

Vercel 에 이 레포를 연결하고, 프로젝트 설정의 Environment Variables 에
`SUPABASE_URL` 과 `SUPABASE_ANON_KEY` 를 넣는다. 배포 주소로 QR 을 만들어 배포한다.

## 지금 상태 (2026-09-19)

**수집 파이프라인이 살아 있다.** 폼 제출 → Supabase 저장 → 주차 이벤트 자동 생성까지 확인됨.

```
[선배] Vercel 폼 ──▶ /api/reports ──▶ Supabase
                                        report      1행
                                        load_event  N행  ← 트리거가 자동 생성
                                        v_week_load      ← 진단 기능이 읽을 뷰
```

| | 상태 |
|---|---|
| 주제·범위, 설계 계획서 | ✅ |
| Supabase 스키마 (테이블 7개 · 트리거 · RLS · 뷰) | ✅ 적용 완료 |
| 입력 폼 (Next.js + Vercel) | ✅ 배포·제출 확인 |
| 교과과정 `course` 150과목 | ⬜ **다음 병목** |
| 진단 기능 (부담 계산 · 대안 추천) | ⬜ |
| 관심분야 로드맵 | ⬜ |

**계획보다 3주 빠르다.** 설계상 입력 폼은 W4 배포 예정이었는데 시작 전에 끝났다.
그만큼 선배 응답 수집 기간이 길어졌다.

### 데이터는 CSV 를 거치지 않는다

진단 기능은 `v_week_load` 를 **실시간으로 조회**한다. CSV 는 백업·엑셀 확인·발표 자료용이며
앱의 데이터 경로가 아니다. CSV import 가 필요한 곳은 두 군데뿐이다 —
교과과정표 일괄 입력, 그리고 프로토타입 데이터 이관.

### 알려진 과제

- **과목명이 자유 입력이다.** `자동제어1` · `자동제어 1` 이 다른 과목으로 잡힌다.
  `course` 마스터가 채워지는 대로 **검색·선택으로 교체**해야 한다 (구조 수정 사항)
- 중복 제출 방지와 요청 제한이 없다 — **QR 배포 전에** 넣어야 한다

## 일정의 핵심

**입력 폼을 진단 기능보다 먼저 배포한다 (W4).**
모든 기능이 선배 데이터에 의존하는데, 개발을 끝내고 수집을 시작하면 학기가 끝난다.
수집 기간 7주 이상 확보가 목표다. 공개 전에 팀원이 먼저 채워 빈 서비스를 피한다.

자세한 주차별 계획은 `docs/plan/학업나침반-설계계획.pdf` §10.
