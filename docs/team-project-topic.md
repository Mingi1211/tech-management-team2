# 팀 프로젝트 주제안 — `학기예보`

> 수강 조합의 학기 중 부담을 예보하고, 뺄 과목을 캐릭터가 집어주는 서비스
>
> 팀 구성: 8명 (로봇학부 + 소프트웨어 + 전자) · 하드웨어 설계 없음 · 웹 서비스
> 참고: A팀(장박사) "월계동 맛집 추천 웹서비스" 회의록 / Project Charter 양식 PPT

## 0. 주제 선정 경과

| 검토 | 주제 | 판단 |
|---|---|---|
| 1차 | 자연어 로봇 동작 시뮬레이터 | 전공 심화 성격 과다 → 탈락 |
| 2차 | 캠퍼스 공간·장비 통합 예약 | 학교 DB·행정 권한 의존 → 탈락 |
| 3차 | 졸업요건 자가진단 | KLAS에 졸업심사 기능 존재 + 민감 사안 → 탈락 |
| **4차 (확정)** | **수강 조합 부담 예보 + 캐릭터 공유** | — |

### 누적된 선정 기준
1. **외부 기관의 협조·권한·데이터 제공이 필요하지 않을 것**
2. 학교 공식 시스템이 이미 제공하는 기능과 겹치지 않을 것
3. 틀렸을 때 사용자에게 돌이킬 수 없는 피해를 주지 않을 것
4. **개인정보를 수집하지 않고도 작동할 것** ← 이번 회차에서 추가

## 1. 문제 정의 (Why)

### 한 문장 문제 정의
> **수강신청은 "요일과 시간"으로만 짜는데, 학기를 실제로 망가뜨리는 것은 "10주차에 몰린 부담"이다.**

### 왜 지금 수단으로는 안 되는가

| 기존 수단 | 무엇을 하는가 | 무엇을 못 하는가 |
|---|---|---|
| **에브리타임 시간표 마법사** | 시간이 겹치지 않는 **모든 조합**을 자동 생성 | 요일·시간 축만 본다. 학기 중 어느 시점에 부담이 몰리는지 고려하지 않음 |
| **에브리타임 강의평** | 과목별 후기 텍스트 | **"이 6과목을 같이 들으면 어떻게 되는가"** 는 아무도 안 알려줌 |
| **강의계획서** | 평가비중·주차별 계획(공식) | 과목별로 흩어져 있어 조합해서 볼 수 없음 |

**공백: 조합 단위로, 시간축이 아니라 학기축으로 부담을 보여주는 도구가 없다.**

### 타깃 사용자
2학년 이상 중 **학기 외에 반드시 지켜야 할 일정이 있는 사람** — 취업 준비 고학년, 학부연구생, 공모전·대외활동 병행자.
이들의 니즈는 "쉬운 시간표"가 아니라 **"부담이 한 시기에 몰리지 않는 시간표"** 다.

## 2. 핵심 설계 판단 ① — 데이터 불확실성을 어떻게 다루는가

### 지적된 문제
> "같은 수업이라도 교수님이 다음 학기에 운영을 달리할 수 있고, 과제를 언제 얼마나 내주는지·시험 난도와 횟수는 직접 들은 사람 아니면 알기 힘들다."

**이 지적은 옳다. 그래서 제품의 정의 자체를 바꾼다.**

### 2-1. "난이도 판정"이 아니라 "부담 예보"
절대 난이도를 주장하는 순간 반박당한다. 서비스의 은유를 **일기예보**로 잡는다.

> **예보는 원래 확률이다.** 우리는 정답을 말하지 않고 확률과 신뢰도를 함께 제시한다.
> 사용자도 "강수확률 60%"를 정답으로 받아들이지 않으면서 우산은 챙긴다.

이 프레이밍 하나로 데이터 불확실성이 **결함에서 전제로** 바뀐다.

> ⚠️ 다만 **날씨 아이콘·날씨 이름을 UI에 쓰지는 않는다.** "폭풍"은 이미 다들 아는 비유라 신선하지 않고,
> 화면에서 기억에 남는 것은 날씨가 아니라 캐릭터여야 한다. "예보"는 **불확실성을 다루는 논리**로만 남기고,
> 등급의 얼굴은 §4의 캐릭터 반응 5단계가 맡는다.

### 2-2. 교수가 바뀌어도 살아남는 신호만 쓴다

| 쓰는 신호 (안정적) | 안 쓰는 신호 (휘발적) |
|---|---|
| **부담의 형태** — 시험형 / 과제형 / 프로젝트형 / 출석형 | 과제 정확한 개수 |
| **부담의 시점** — 중간·기말 집중형 vs 상시 누적형 | 시험 문항 난도 |
| **평가비중** (강의계획서 공식 기재) | 교수 개인의 채점 성향 |
| **조합 충돌** — 같은 형태의 부담이 겹치는가 | 학점 잘 주는지 여부 |

**핵심 논리: 개별 과목 정보가 다소 부정확해도 "프로젝트형 3과목 동시 수강은 위험하다"는 결론은 교수가 누구든 성립한다.**

### 2-3. 데이터 단위는 `과목 × 교수 × 학기`
교수가 바뀌면 이전 학기 데이터는 자동으로 신뢰도 강등. 화면에 **"2025-2학기 · ○○○ 교수 기준"** 을 항상 병기.

### 2-4. 신뢰도 등급을 전면에 표시

| 등급 | 조건 | 표기 |
|---|---|---|
| **A** | 강의계획서 + 수강 경험자 3명 이상 검증 | 초록 · "검증됨" |
| **B** | 강의계획서만 | 노랑 · "공식 자료 기반" |
| **C** | 담당교수 변경 / 데이터 부족 | 회색 · **"정보 부족 — 참고만"** |

> "이 과목은 정보가 부족합니다"라고 정직하게 말하는 것이, 틀린 숫자를 자신 있게 보여주는 것보다 강하다.

## 3. 핵심 설계 판단 ② — 개인정보를 아예 받지 않는다 ⚠️

### 변경 사유
이전 안은 사용자의 학기 외 일정(취준·랩·공모전)을 먼저 입력받아 겹쳐 그리는 구조였다.
**그러려면 일정 정보 수집·동의 절차가 필요하고, 프로토타입이 애플리케이션 단계까지 갈지 미지수인 상황에서 과도한 설계다.**

### 변경 내용
> **개인 일정 입력을 전면 제거한다. 대신 시간표를 짠 뒤 "상세보기"에서 주차별 브리핑을 제공한다.**

```
[결과 화면]        이번 학기 난이도 87점 · 폭풍 ⛈
[주차별 타임라인]  ▁▂▃▅███▅▃▂▁▂▃██▅▂
                            ↑
[상세보기 · 10주차]
  "과제 3개 · 프로젝트 중간발표 1개 · 중간고사 2개가 겹칩니다.
   이번 학기 최대 고비입니다."
```

**사용자는 이 브리핑을 자기 일정과 머릿속에서 대조한다. 우리는 정보만 제공한다.**

### 이 변경이 오히려 나은 이유
- **로그인 0 / 회원가입 0 / 개인정보 수집 0** — 발표에서 "개인정보는요?"에 한 문장으로 끝난다
- 첫 화면에서 바로 써볼 수 있어 진입장벽이 사라진다 (공유 바이럴에 필수)
- 구현 범위가 줄어 **재미 레이어(§4)에 역량을 집중**할 수 있다
- 캘린더 연동·알림 푸시는 "향후 과제"로 발표하면 확장성 어필이 된다

> 취준·연구생 프리셋은 삭제가 아니라 **확장 기능으로 보류**한다. 필요해지면 서버 저장 없이 브라우저 안에서만 겹쳐 보는 방식으로 구현한다.

## 4. 핵심 설계 판단 ③ — 재미와 공유가 기능이다 ⭐

### 문제 인식
> "그냥 시간표 짠 거에 대해 난이도 평가하고 끝이면 식상하다."

맞다. **부담 예보는 진지해서 아무도 안 들어온다. "우니가 뭐래?"는 들어온다.**

### 4-1. 점수는 사용자에게 보여주지 않는다 ⭐

"100점 만점에 87점"은 솔직히 와닿지 않는다. 사용자는 이미 단계만 봐도 감을 잡는다.
**그래서 점수는 화면에서 빼고, 백엔드의 판단 재료로만 쓴다.**

```
[백엔드에서만 계산]          [임계치로 단계 결정]        [역산 — 여기가 핵심]
 매주 과제      +10           81 이상  최고 경보         82 − 10(매주 과제)
 팀 프로젝트    +15           61–80   경고                 − 15(팀 프로젝트) = 57
 시험 3회       +8            41–60   음…
 발표 2회       +6            21–40   할 만해           → "디지털시스템설계를 빼면
 기타 과목 합   +43           20 이하  놀자                 두 단계 내려갑니다"
 ─────────────
 합계            82
```

**점수의 진짜 용도는 표시가 아니라 역산이다.**
"어떤 과목을 빼면 단계가 내려가는가"를 계산해 **행동 가능한 제안 한 줄**로 바꾼다.
사용자에게 남는 문장은 "87점"이 아니라 **"이거 빼면 두 단계 내려간다"** 이다.

### 4-2. 캐릭터 반응 5단계 — 등급의 얼굴

| 단계 | 이름 | 표정 | 멘트 (예시) |
|---|---|---|---|
| 1 | **놀자** | 활짝 · 만세 | "이 정도면 산책이지~ 동아리 하나 더?" |
| 2 | **할 만해** | 미소 | "사람답게 살 수 있는 학기예요" |
| 3 | **음…** | 무표정 · 식은땀 | "평범한 광운인의 학기. 평범이 제일 무섭죠" |
| 4 | **야, 잠깐** | 놀람 | "10주차에 우산으로는 안 됩니다" |
| 5 | **그것만은 안 돼** | 절규 | "제발 한 과목만 빼주세요…" |

### 4-3. 핵심 연출 — "팔 내리기" 제스처 GIF ⭐

최고 단계에서 캐릭터가 **두 팔을 아래로 끝까지 내리는 짧은 루프 GIF**를 춘다.
"부담을 내려라 = 과목을 빼라"는 뜻이 동작 하나로 전달된다.

```
프레임 1: 팔 올림  →  프레임 2: 내리는 중  →  프레임 3: 끝까지 내림 (반복)
                                            + "그것만은 안 돼…"
```

**이 연출이 중요한 이유: 재미 요소가 곧 기능이다.**
팔을 내리는 동작이 그대로 §4-1의 **"이 과목을 빼세요" 추천**을 가리킨다.
장식으로 붙인 캐릭터가 아니라, 제품의 핵심 기능을 전달하는 인터페이스다.

> **IP 주의** — 착안은 어디서 했든, 구현은 **실제 인물·영상·음원·특정 안무를 일절 사용하지 않는다.**
> 자체 제작 캐릭터가 하는 일반적인 "팔 내리기" 동작으로만 만들고, 특정 인물이나 곡을 지칭하지 않는다.
> 발표 자료에도 실존 인물 이미지를 넣지 않는다.

### 4-4. 점수보다 "유형" — MBTI식 공유 욕구 활용

단순 점수는 한 번 보고 끝난다. **유형에는 이름이 붙고, 이름이 붙으면 공유된다.**
부담 프로파일을 4축으로 분해해 16유형을 만든다.

| 축 | 한쪽 | 반대쪽 |
|---|---|---|
| 부담 분포 | **S** 분산형 (상시 조금씩) | **C** 집중형 (중간·기말 몰빵) |
| 평가 방식 | **E** 시험 중심 | **A** 과제 중심 |
| 수행 단위 | **T** 팀플 다수 | **I** 개인 과제 다수 |
| 총량 | **H** 고부담 | **L** 저부담 |

예: `CETH` = **"벼락치기 팀플 지옥러"**, `SAIL` = **"잔잔바리 마라톤러"**

> 16유형 각각에 이름·설명·궁합(같이 들으면 좋은 과목 유형)을 붙인다. **유형 이름 짓기는 개발이 아니라 기획 작업이라 비개발 팀원이 주도할 수 있다.**

### 4-5. 공유 카드 — 바이럴의 실체

결과를 **이미지 카드 한 장**으로 만들어 인스타 스토리·에타·카톡에 바로 올릴 수 있게 한다.

```
┌─────────────────────────┐
│   2026-1학기 학기예보      │
│                          │
│      [예보관 캐릭터]       │
│         ⛈                │
│                          │
│    난이도 87점 · 폭풍       │
│    「벼락치기 팀플 지옥러」   │
│                          │
│  "제발 한 과목만 빼주세요"   │
│                          │
│   10주차 최대 고비 ⚠        │
└─────────────────────────┘
```
- 기술: SVG/Canvas → PNG 다운로드. **난도 낮고 임팩트 크다**
- 카드에 서비스 링크 포함 → 본 사람이 자기 시간표를 넣어본다

### 4-6. 대화거리를 만드는 기능

| 기능 | 내용 |
|---|---|
| **친구와 비교** | 공유 링크로 들어온 친구가 자기 조합을 넣으면 "너 87점, 나 62점" 비교 화면. **로그인 없이 URL에 조합을 인코딩** |
| **익명 랭킹** | "로봇학부 24학번 평균 64점 · 당신은 상위 12%" |
| **명예의 전당** | 이번 학기 최고 난이도 조합 익명 공개 (자발적 제출만) |

### 4-7. 왜 이것이 "장난"이 아니라 기능인가 (발표 논리)

1. **바이럴이 곧 데이터 수집이다.** 공유 → 유입 → 학기말 회고 입력 증가 → 예보 정확도 상승. **재미가 서비스 품질에 직결되는 선순환 구조**
2. **진입장벽 제거.** 개인정보도 로그인도 없으니 링크 하나로 즉시 체험
3. **커뮤니티 대화 소재** — 단순 도구가 아니라 학기 초 캠퍼스의 공통 화제가 되는 것이 목표

## 5. 캐릭터 저작권 — 우니를 쓸 수 있는가 ⚠️

### 조사 결과

| 항목 | 내용 |
|---|---|
| 정체 | 광운대 마스코트 **우니** (하위 캐릭터 팡이). 상징동물 **비마(飛馬, 페가수스)** 를 재해석 |
| 출처 | 2021년 학부생 대상 마스코트 공모전 1위작 |
| 사용 절차 | 홍보 페이지에 **「마스코트 사용 확인 신청서」** 및 **「마스코트 2차 가공 사용 확인 신청서」** 양식이 별도로 존재 |

**우리가 하려는 "표정을 5단계로 바꾸는 것"은 명백한 2차 가공** → 2차 가공 신청서 제출 및 승인 필요.

### 판단
> **우니에 의존하는 설계는 선정 기준 1번(외부 협조 불필요)에 정면으로 위배된다.**
> 승인이 늦거나 거절되면 서비스의 얼굴이 통째로 사라진다.

### 해결 — 투트랙 + 스킨 구조

```
[캐릭터 레이어를 교체 가능한 "스킨"으로 설계한다]

  기본 스킨 (Plan A) : 팀 자체 제작 오리지널 캐릭터  ← 프로젝트는 이것만으로 완결
  추가 스킨 (Plan B) : 우니 (2차 가공 승인 시에만 활성화)
```

- **Plan A로 프로젝트를 완성한다.** 승인 여부와 무관하게 발표 가능
- 병행해서 홍보팀에 2차 가공 신청서를 제출해 둔다. 승인되면 "우니 스킨"을 추가로 붙인다
- 승인이 나오면 **"학교 공식 마스코트와 협업한 서비스"** 라는 강력한 발표 소재가 된다. 안 나와도 잃는 것이 없다
- 스킨 구조 자체가 **확장성 있는 설계**라 기술적으로도 설명할 거리가 된다

### Plan A 권장안 — 「구름이」(가칭)

> **교명 광운(光云)의 '운(云/雲)'이 구름을 뜻한다는 데서 착안한 구름 캐릭터.**
> ※ 한자 어원은 발표 전 학교 공식 자료로 확인할 것

- **일기예보 컨셉과 100% 일치** — 난이도가 오르면 흰 구름 → 먹구름 → 번개 구름
- 우니(페가수스)보다 오히려 날씨 은유에 맞는다
- **SVG 도형으로 그리기 쉽다** — 원 몇 개 + 눈·입 path. 표정 5단계는 path만 교체
- 이미지 파일 없이 **코드로 그리므로** 저작권 완전 클린, 용량 0, 애니메이션 자유
- 교명에서 따왔다는 설명 한 줄로 광운대 학생의 소속감을 건드린다

### 저작권 문제 없는 대안 에셋 (Plan A가 어려울 경우)

## 6. 무엇을 만드는가 (What)

### 한 줄 정의
> **시간표 마법사가 요일·시간의 빈칸을 채운다면, `학기예보`는 학기 중 에너지의 빈칸을 보여주고 — 그 결과를 친구에게 자랑하게 만든다.**

### MVP 기능 (반드시 구현)

1. **과목 담기** — 개설 과목에서 조합 구성, 여러 조합 저장·비교 (로그인 없이 브라우저 저장)
2. **부담 5단계 판정** — 점수는 내부에만, 화면에는 단계와 캐릭터만
3. **캐릭터 반응 + 팔 내리기 GIF** ★ — 표정 5단계, 최고 단계에서 제스처 루프
4. **주차별 부담 타임라인** — 16주에 부담을 배분한 히트맵/그래프
5. **주차별 상세 브리핑** ★ — 주차를 누르면 "과제 3개 · 발표 1개 · 시험 2개가 겹칩니다"
6. **뺄 과목 역산 제안** ★ — "이 과목 하나만 빼면 두 단계 내려가요" + 조합 경고
7. **학기 유형 진단(16유형)** ★ — 유형명 + 설명
8. **공유 카드 생성** ★ — PNG 다운로드 + 링크 공유
9. **신뢰도·근거 표시** — 과목별 A/B/C 등급, 기준 학기, 담당교수
10. **대안 제시** — 같은 이수구분 안에서 부담 형태가 다른 대체 과목 추천

### 확장 기능 (여유 시)
11. 친구와 비교 (URL 인코딩 방식)
12. 학부·학번별 익명 랭킹
13. 학기말 회고 30초 입력 (데이터 축적 루프)
14. 최소 부담 조합 자동 탐색
15. 개인 일정 오버레이 (브라우저 내 처리, 서버 저장 없음)
16. 우니 스킨 (2차 가공 승인 시)

### 범위 밖 (명시적으로 안 함) ⚠️
- **교수 개인에 대한 평가·랭킹·점수화** — 과목의 성격만 다루고 사람을 평가하지 않는다
- 성적(학점) 예측
- **개인정보 수집, 회원가입, 캘린더 연동** — 이번 회차에서 명시적으로 제외
- 수강신청 대행·매크로, 학교 DB 연동, 크롤링
- 하드웨어·회로·기구 설계

## 7. 데이터를 어떻게 확보하는가

| 단계 | 출처 | 담당 | 커버리지 |
|---|---|---|---|
| **1차 — 팀 내부 경험** | **팀원 8명이 이미 수강한 과목** | 전원 | 1인당 20~30과목 → 중복 제외 **80과목 이상** |
| **2차 — 공식 문서** | 강의계획서의 평가비중·주차별 계획 | 조사 담당 2명 | 개설 전공과목 전반 |
| **3차 — 선배 설문** | 구글폼 (학부 단톡방·학회 배포) | 기획 담당 | 목표 응답 50명 |

> **1차가 핵심이다.** 8명이 이미 들은 과목만으로 서비스가 즉시 작동한다. 외부 협조 0.
> A팀이 메뉴판을 직접 촬영한 것과 같은 구조이며, "데이터는 어떻게 모았나요?"에 **"저희가 직접 들은 과목부터 시작했습니다"** 로 답할 수 있다.

### 수집 항목 (설문·엑셀 칼럼 확정안)
`순번 / 학부 / 과목명 / 학수번호 / 담당교수 / 수강학기 / 이수구분 / 학점 / 평가비중(중간·기말·과제·출석·기타) / 부담형태(시험형·과제형·프로젝트형·출석형) / 과제 주기(매주·격주·비정기·없음) / 팀프로젝트 유무 / 발표 유무 / 시험 횟수 / 부담 집중 주차(복수 선택) / 체감 부담(1~5) / 응답자 유형(팀원·선배) / 신뢰도 등급 / 최종 확인일`

## 9. 예상 공격 질문 & 방어 ⭐

| # | 예상 질문 | 답변 |
|---|---|---|
| 1 | **교수님이 바뀌면 데이터가 무용지물 아닌가요?** | `과목 × 교수 × 학기`로 관리하고 교수가 바뀌면 신뢰도를 자동 강등합니다. 주 신호도 과제 개수가 아니라 **잘 안 변하는 부담 형태**입니다 |
| 2 | **직접 들은 사람 아니면 모르는 정보 아닌가요?** | 맞습니다. 그래서 **팀 8명이 들은 과목**을 1차 데이터로 삼고, 모르는 과목은 "정보 부족(C)"으로 표시합니다 |
| 3 | **시간표 마법사와 뭐가 다른가요?** | 마법사는 **요일·시간** 축, 저희는 **학기 16주** 축입니다 |
| 4 | **개인정보 수집은요?** | 수집하지 않습니다. 로그인도 회원가입도 없고, 조합은 브라우저에만 저장됩니다 |
| 5 | **학교 마스코트를 마음대로 써도 되나요?** | 기본 캐릭터는 **팀이 직접 만든 오리지널**입니다. 우니는 2차 가공 승인을 받은 경우에만 추가되는 선택 스킨으로 설계했습니다 |
| 6 | **교수님 평가 서비스 아닌가요?** | 아닙니다. 교수 개인에 대한 점수·랭킹은 **기능 범위에서 명시적으로 제외**했습니다 |
| 7 | **재미 요소는 본질이 아니지 않나요?** | 공유가 늘면 회고 데이터가 쌓이고 예보 정확도가 올라갑니다. **재미가 데이터 품질에 직결되는 구조**입니다 |
| 8 | **예측이 틀리면요?** | 판정이 아니라 **예보**입니다. 신뢰도를 항상 함께 표시하고, 지난 학기 수강생 15명과 소급 대조해 정확도를 수치로 공개합니다 |
| 9 | **기술적으로 쉬운 것 아닌가요?** | 난도의 핵심은 **부담을 주차 단위로 모델링하는 규칙 설계**와 **16유형 분류 로직**, 그리고 공유 카드 렌더링입니다 |
| 10 | **왜 광운대만 하나요?** | 학교마다 커리큘럼이 달라 **한 학교를 깊게 파는 쪽이 유리한 구조**입니다 |

## 10. 기술 스택 (전부 무료 / 저비용)

- 프론트: React + TypeScript + Vite, 반응형(모바일 우선 — 공유가 목적이므로 필수)
- **캐릭터**: 자체 제작 **인라인 SVG** (표정 5단계를 path 교체로 구현, 이미지 파일 불필요)
- 시각화: 주차별 부담 타임라인 (경량 차트 라이브러리 또는 자체 SVG)
- **부담 모델링 엔진**: 평가비중·부담형태를 16주에 배분하고 조합 위험을 탐지하는 자체 모듈
- **공유 카드**: Canvas 또는 SVG → PNG 변환 후 다운로드
- 백엔드: FastAPI 또는 Next.js API Route / DB: PostgreSQL (Supabase 무료 티어)
- 설문: Google Forms → CSV → DB 이관 / 배포: Vercel 무료 티어
- 개발 도구: Cursor, Claude Code / 협업: GitHub, Notion, Figma

| **재미 요소가 유치해 보임** | 멘트·유형명을 사용자 테스트로 검증하고, 공격적·비하적 표현은 배제. 난이도 수치와 근거는 항상 함께 표시해 **근거 있는 유머**로 유지 |
| **설문 응답 부족** | 팀 내부 8명 경험만으로 MVP 작동. 설문은 정확도 향상용 |
| **교수·학과의 부정적 반응** | 교수 평가·랭킹 원천 배제. 발표 전 지도교수 사전 공유 |
| **범위 확대** | 3개 학부 전공과목 80개로 못 박는다. 교양은 범위 밖 |
| 통합 지연 | 매주 화요일 회의에서 `main` 통합 강제 |

## 15. 최종 발표 데모 시나리오 (5분)

1. 문제 제기 — 시간표 마법사 화면 한 장. **"이 도구는 요일과 시간만 봅니다. 그런데 학기를 망치는 건 10주차입니다"**
2. 과목 6개 담기 → **「그것만은 안 돼」** 단계 + 캐릭터가 팔을 내리며 절규하는 GIF (여기서 웃음)
3. 주차별 타임라인 → **10주차 클릭** → "과제 3개 · 발표 1개 · 시험 2개가 겹칩니다"
4. **"빼보기"** 누르기 → 타임라인이 평탄해지고 캐릭터 표정이 두 단계 풀리는 **before/after**
5. **학기 유형 「벼락치기 팀플 지옥러」** 진단 → **공유 카드 생성** → 실제로 휴대폰에 뜨는 장면
6. 신뢰도 "정보 부족(C)" 화면을 **일부러 보여주며** 정직성 강조
7. 성과 정리 — 80과목 커버리지, **소급 검증 정확도**, 사용자 테스트 20명, **공유 카드 생성 횟수**
